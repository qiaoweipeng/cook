# 踩过的坑

> 按类别整理三个版本踩过的所有坑。每个坑带**现象 → 根因 → 修法 → 纪律**四要素。
> 版本迭代历史见 [CHANGELOG.md](./CHANGELOG.md)，架构设计见 [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 后端 / 计费

### 坑 1：CloudBase 体验版三天烧完资源点（起始版本）

| 项 | 内容 |
|----|------|
| **现象** | 打开 App → 数据库 503 被隔离 → 控制台导出也挂了 → **数据导不出来** |
| **根因** | 不是存储不够，是 **CU（CPU 核·小时）烧完了 3000 点**。占比 97%（8.48 核·时 × 342 点/核·时）。存储容量才花了 1 点 |
| **为什么 CPU 这么高** | Base64 图片塞数据库 + 全量拉五张表 + 没指定列。每次 `SELECT dishes` 把几 MB Base64 一起拉，PostgreSQL 序列化大字段吃 CPU |
| **对比 Supabase 为什么稳** | Supabase 按磁盘容量计费（500 MB 封顶），不按 CPU。同样的代码在 Supabase 上额度根本用不满 |
| **纪律** | 免费 BaaS 先搞清楚**按什么计费**——是按读次数？按 CPU？按磁盘？按流量？选和你的数据形态匹配的 |

### 坑 2：Supabase Storage 下行流量烧完（v1.0）

| 项 | 内容 |
|----|------|
| **现象** | 菜单卡片全裂图（403 / 限速），数据库本身还能用 |
| **根因** | Supabase 免费版 **5 GB/月 egress**。每次打开 App 一次性拉所有菜单封面（几十道 × ~200KB） |
| **修法** | Provider 抽象 + 切腾讯 COS（下行流量 0.8 元/GB，按需付） |
| **纪律** | 对象存储**下行流量是最贵的资源**。CDN 缓存（`immutable` + `loading="lazy"`）比换平台更重要 |

### 坑 3：CloudBase 隔离后不让导出（起始版本）

| 项 | 内容 |
|----|------|
| **现象** | 资源点耗尽 → 数据库隔离 → 控制台导出接口也一起挂了 |
| **根因** | CloudBase 的隔离是**全链路**的——PostgREST、控制台查询、导出接口一起挡 |
| **纪律** | 任何托管服务都要有**独立的备份通道**，不能依赖控制台导出。本地 `pnpm backup` 脚本必须跑起来 |

### 坑 4：CloudBase 静态托管注入 index.html（起始版本）

| 项 | 内容 |
|----|------|
| **现象** | 刷新页面偶尔跳出 CloudBase 自己的 index 页面、冒 `Download.html` |
| **根因** | CloudBase 托管不是纯 SPA 托管 |
| **修法** | 换 Netlify（`/* → /index.html` 完美 SPA 回退） |
| **纪律** | SPA 项目**必须选支持 SPA 回退**的托管方案 |

## 图片存储

### 坑 5：Base64 塞数据库（起始版本 + v1.0 早期）

| 项 | 内容 |
|----|------|
| **现象** | CloudBase 烧 CU、Supabase 单次全量同步拉 60 MB、5 GB 流量只够 80 次 |
| **根因** | 图片是二进制大对象，数据库 text 列存它会：① 每次 SELECT 都要序列化几 MB ② 吃数据库 I/O ③ 每次请求都重拉（浏览器不能缓存 API 响应） |
| **修法** | 三件事一起做：① **迁到对象存储**（数据库只存 key，浏览器直接拉 CDN，浏览器能缓存）② **全部转 WebP 格式**（比 JPEG/PNG 小 25-35%）③ **上传前压缩**（最长边缩到 1000px + WebP quality 0.82，肉眼无损）。三步加起来，一张 2MB 原图能压到 100-200 KB |
| **纪律** | **图片永远不要存数据库**（除非只有几张小图标）。对象存储是唯一正确选择 |

### 坑 6：模块级标志位永久降级（图片消失第一回）

| 项 | 内容 |
|----|------|
| **现象** | 图片传了、Storage 里也有、界面提示已保存 → 换个设备/清缓存 → 全没了 |
| **根因** | `coverImageColumnMissing` 模块级 boolean，一次误判后整个页面生命周期内所有菜品都不再存图片地址。上传失败还静默降级成 Base64（又是假成功） |
| **修法** | 列缺失直接抛错，绝不静默跳过。删掉 Base64 降级分支，上传失败就是失败 |
| **纪律** | ① **错误要暴露，不要吞**——宁可让保存报错，也不能假装成功 ② 模块级标志位做降级开关**极其危险** |

### 坑 7：拉取失败被当成空表 → 种子覆盖（图片消失第二回）

| 项 | 内容 |
|----|------|
| **现象** | 用户上传的图地址被代码悄悄覆盖成 null，操作日志显示没动过图片字段 |
| **根因** | 三个 bug 连环撞：① `cloudList` 吞错返回 `[]` ② `load()` 把 `[]` 误判为"云端空表" → 触发种子全量覆盖 ③ `update()` 的 spread 合并不区分"未提供"和"提供为 undefined" |
| **修法** | ① 拉取失败直接 return，不写云端 ② update 过滤 patch 里的 undefined ③ 保存后**回读校验**——写入后立刻 SELECT 比对，当场发现不一致 |
| **纪律** | ① `[]` ≠ 空数据，**吞错降级后的返回值绝不能作为触发写入的依据** ② spread 合并 patch 前先想语义——「字段没提供」和「字段提供为空」是两回事 ③ 全量覆盖类操作是最高危操作 |

### 坑 8：相对路径被当成完整 URL 用

| 项 | 内容 |
|----|------|
| **现象** | 数据库里 `cover_image` 混着三种形态（完整 URL / `/dishes/a.jpg` / Base64），直接当 `<img src>` 用会把相对路径拼成"你自己域名下的 `/dishes/a.jpg`" → 404 |
| **修法** | 渲染前一律过 `resolveImageUrl()`，统一转完整 CDN URL |
| **纪律** | 数据库只存**相对 key**，不存完整 URL。URL 只在渲染时拼接 |

### 坑 9：上传 + 写库没有补偿事务

| 项 | 内容 |
|----|------|
| **现象** | 图片传成功了但数据库写失败 → 对象存储里留了没人引用的孤儿图 |
| **修法** | 补偿事务：保存失败/用户取消时，把刚传的图删掉。用 `pendingUploadRef` 记下待提交状态 |
| **纪律** | 跨系统多步操作必须有**撤销路径**。上传 + 写库这种分两步的流程，不能只实现成功路径 |

## 数据库

### 坑 10：种子数据和外键冲突（起始版本）

| 项 | 内容 |
|----|------|
| **现象** | 种子数据写入顺序不受控（菜品可能先于食材写入），加了外键会在初始化时冲突 |
| **修法** | 建表脚本**不加外键**。种子脚本只管数据顺序 |
| **纪律** | 种子数据场景下，外键约束是麻烦制造者。用代码逻辑保证数据一致性 |

### 坑 11：RLS 全开 + 拿错 key

| 项 | 内容 |
|----|------|
| **现象** | RLS 开启但没建 policy → 前端读到空数组（不是报错），容易误判成没数据 |
| **纪律** | ① RLS 一旦开启**必须立刻建 policy** ② 绝对不要用 Secret key / service_role key（绕过全部 RLS） |

## 前端 / 性能

### 坑 12：localStorage 只有 5MB

| 项 | 内容 |
|----|------|
| **现象** | 几道菜的 Base64 图片就把 localStorage 撑满了 |
| **修法** | 换成 IndexedDB（理论上几百 MB 上限） |
| **纪律** | localStorage 只存小量字符串（token、配置），**不要存图片或大数据** |

### 坑 13：性能预算超标（单 chunk 3 MB）

| 项 | 内容 |
|----|------|
| **现象** | antd + antd-mobile + xlsx 全塞一个 chunk，手机上永远用不到 PC 端组件但照样要下载 900 KB（gzip） |
| **根因** | 没有按"谁用 / 在哪用"拆 chunk |
| **修法** | `manualChunks` 把 PC UI、Mobile UI、Excel 工具、特效分开；场景特定的库用 `import()` 动态加载 |
| **纪律** | **两个 UI 库（antd + antd-mobile）不能共存一个 chunk**，必须拆。Excel 导出这种低频功能必须点了才加载 |

### 坑 14：iPad Pro 12.9 竖屏和 iPad 9.7 横屏宽度同为 1024

| 项 | 内容 |
|----|------|
| **现象** | 纯宽度断点区分不了"竖 3 横 4"，Pad 竖屏应该显示 3 列但被误判成横屏显示 4 列 |
| **修法** | 方向 + 宽度**联合判定**，用 `useIsPadPortrait` hook |
| **纪律** | iPad 不是"大一点的手机"，横屏竖屏是两个不同的使用场景 |

### 坑 15：横过来宽度超 768 会被误判成 PC

| 项 | 内容 |
|----|------|
| **现象** | 手机横过来打开 PC 端页面，布局全乱 |
| **修法** | 手机判定用 **UA**，不用宽度 |
| **纪律** | 移动设备判定：**UA 判断设备类型，宽度判断当前方向**，两者分工不同 |

## PWA / iOS 推送（全是静默丢弃型）

iOS PWA 推送是 Web Push 里最玄学的部分——**服务端 APNs 返回 201 = 看起来发出去了，Safari 解不开就静默丢弃整条通知**，没有报错、没有日志、没有任何线索。下面这些坑每一个都能让你调几天。

### 坑 16：Safari / iOS 只认早期草案的 HKDF 加密算法

| 项 | 内容 |
|----|------|
| **现象** | 服务端推送 APNs 返回 201，手机端毫无反应 |
| **根因** | Web Push 加密有两个版本：RFC 8291（2017 定稿，Chrome 用这个）和**早期草案**（Safari / iOS 只认这个）。两套算法的 HKDF info 标签、context 结构完全不同 |
| **修法** | 按早期草案写：`info = "WebPush: info\0" + uaPublic + asPublic`（无长度前缀），不是 RFC 8291 的 `"Content-Encoding: aes128gcm\0" + "P-256\0" + context` |
| **纪律** | Web Push 加密必须按 Safari 的写法来，牺牲 Chrome 的 RFC 合规。Chrome 两边都能解 |

### 坑 17：aes128gcm body 的 rs 必须硬写 4096

| 项 | 内容 |
|----|------|
| **现象** | 同上——APNs 201，手机没反应 |
| **根因** | 图省事把 rs 写成 `ciphertext.length`（跟着 payload 长度浮动），Safari 解不开就静默丢弃 |
| **修法** | rs 硬写 **4096**（规范推荐值），不管 payload 多长。临时公钥（65 字节）放进 keyid |
| **纪律** | aes128gcm body 布局的每一个字节都不能改：`salt(16)|rs(4)|idlen(1)|keyid|ciphertext`，plaintext 末尾必须补 `0x02` |

### 坑 18：Service Worker ready 不代表已经 claim() 了页面

| 项 | 内容 |
|----|------|
| **现象** | `ready` 之后立刻 `subscribe()` 成功返回了 PushSubscription（有 endpoint 有密钥），但之后每条推送 Safari 解不开静默丢弃 |
| **根因** | iOS 上 `ready` 只保证 SW 激活完成，**不保证它已经 `clients.claim()` 接管了当前页面**。窗口期订阅 = 浏览器密钥和 SW 私钥对不上 |
| **修法** | 等 `controllerchange` 事件（SW 调 `claim()` 后才触发）再 subscribe。加 5 秒超时保护 |

### 坑 19：iOS 上 unsubscribe 后立刻 subscribe 会拿到错密钥

| 项 | 内容 |
|----|------|
| **现象** | 重新订阅后推送又静默丢弃了 |
| **根因** | iOS push service 在 unsubscribe 之后有清理期，立刻 subscribe 偶尔会生成一对自己都对不上的 p256dh/auth |
| **修法** | ① **优先复用已有订阅**（`getSubscription()` 不是 null 就直接用）② 非要新建时留 800ms 缓冲 |

### 坑 20：iOS 必须从桌面图标打开才能订阅推送

| 项 | 内容 |
|----|------|
| **现象** | Safari 里打开网页，PushManager 存在但 `subscribe()` 直接被拒绝 |
| **根因** | iOS 硬限制——**只有 standalone 模式**（从桌面图标打开）才能订阅推送 |
| **修法** | 用 `isStandalone()` 判断，Safari 里直接给用户说清楚 |

### 坑 21：iOS 权限申请必须在用户手势的同步调用栈里

| 项 | 内容 |
|----|------|
| **现象** | `Notification.requestPermission()` 弹窗不出现、直接返回 `denied` |
| **根因** | iOS 要求权限申请必须在用户点击按钮的同步调用栈里发起。先 `await serviceWorker.ready` 再申请就脱离了同步栈，iOS 直接拒绝 |
| **修法** | **权限申请放在最前面**，不能先 await 别的 |

## 安全

### 坑 22：管理员密码硬编码在前端 bundle

| 项 | 内容 |
|----|------|
| **现象** | `ADMIN_PASSWORD = '000000'` 在 `src/lib/userAdmin.ts`，会被打进 JS bundle。任何人 F12 就能看到 |
| **纪律** | 任何密钥、密码、token 都**不能**硬编码在前端。管理员登录必须走服务端校验 |

### 坑 23：`VITE_` 前缀的环境变量会被打进 bundle

| 项 | 内容 |
|----|------|
| **现象** | COS 的 SecretId/SecretKey 如果叫 `VITE_COS_SECRET_ID`，会被 Vite 编译进 JS bundle |
| **纪律** | 带 `VITE_` 前缀的变量 = 公开变量。云厂商密钥必须放在**服务端**（Netlify Function / Supabase Edge Function） |

### 坑 24：UI 开关不是安全开关

| 项 | 内容 |
|----|------|
| **现象** | `useIsAdmin()` 只判断 `user.id === '0000'`，纯前端布尔值。改一下内存里的 `user` 就能解锁管理界面 |
| **纪律** | UI 只是第一道门。所有写操作必须在**数据库层再校验一次**（RLS policy + 服务端鉴权） |

## 纪律清单（最高优先级）

把上面的教训浓缩成 14 条铁律，code review 时按这个查：

| # | 纪律 |
|---|------|
| 1 | 图片永远不要存数据库（text/blob 列），对象存储是唯一正确选择 |
| 2 | 数据库只存相对 key，不存完整 URL。URL 只在渲染时拼接 |
| 3 | 跨系统多步操作必须有撤销路径（补偿事务） |
| 4 | 错误要暴露，不要吞。宁可让保存报错，也不能假装成功 |
| 5 | 吞错降级后的返回值（如 `[]`），绝不能作为触发写入的依据 |
| 6 | 密钥绝不进前端 bundle。带 `VITE_` 前缀的变量 = 公开变量 |
| 7 | UI 开关不是安全开关，所有写操作必须在数据库层再校验 |
| 8 | 免费 BaaS 先搞清楚按什么计费，选和你的数据形态匹配的 |
| 9 | 备份通道必须独立，不能依赖托管控制台导出 |
| 10 | 两个 UI 库（antd + antd-mobile）不能共存一个 chunk |
| 11 | Web Push 加密**必须按 Safari 的早期草案写**，牺牲 Chrome 的 RFC 合规 |
| 12 | iOS 上 `serviceWorker.ready` 不等于 SW 已接管页面，subscribe 前等 `controllerchange` |
| 13 | iOS 推送权限申请必须放在用户手势同步栈的最前面，不能先 await |
| 14 | iOS 必须从桌面图标打开（standalone）才能订阅推送 |
